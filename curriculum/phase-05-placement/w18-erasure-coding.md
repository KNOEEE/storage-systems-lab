# W18：怎样用更低容量成本获得容错？

## 核心问题

三副本和 `k+m` 纠删码分别依靠什么冗余？容量节省为什么不等于修复或可用性没有代价？

## 理论与设计（1.5 小时）

- [Ceph Architecture](https://docs.ceph.com/en/latest/architecture/)中的副本与纠删码部分，按所用版本查 Pool 与故障域相关约束。
- 回顾 DDIA 第一版第 5 章复制与第 6 章分区；将容量、允许的 shard 丢失和服务可用条件分开。

## 目标源码（1 小时）

固定 Ceph 提交，定位 replicated 与 erasure-coded Pool 的配置表示，以及 EC shard 编码 / 解码接口。只核对数据冗余与恢复输入的边界，不要求读完编码算法。

## 验证步骤（2 小时）

1. 假设固定原始可用容量、均匀放置和大对象，分别计算三副本与给定 `k+m` 的理论有效容量，列出元数据、预留空间等未计入项。
2. 画出具体 host / rack 与 shard 的放置，枚举设备、host、rack 故障，检查剩余 shard 是否足够重建。
3. 分别讨论“数学上能重建”和“当前 Pool 配置允许读写”；依据版本文档核对，不能仅凭 `m` 推断可用性。
4. 与 W15 HDFS 修复比较需要传输与计算的工作。无真实集群测量时只给设计推演，不填恢复速率。
