# W07：为什么写一点，底层却要做很多工作？

## 核心问题

Flush 和 Compaction 各解决什么问题？覆盖和删除后，为什么空间不会立即回收？

## 理论与设计（1.5 小时）

- DDIA 第一版第 3 章：LSM 合并、删除标记与旧版本处理。
- [TiKV B-tree vs LSM-tree](https://tikv.org/deep-dive/key-value-engine/b-tree-vs-lsm/) 的放大指标定义。先明确应用字节、引擎写入字节与设备写入字节的测量层次。

## 目标源码（1 小时）

在固定 RocksDB 提交里定位 Flush 与 Compaction 的任务入口，寻找处理旧版本与删除标记的逻辑和相关测试。核对 snapshot 是否影响版本回收。

## 验证步骤（2 小时）

1. 固定一批键和值大小，记录初次写入后的 SST 数、空间和引擎统计。
2. 对同一批键执行多轮覆盖，再删除其中固定比例；每轮记录逻辑存活数据量和物理空间。
3. 观察后台整理活动，等待或显式触发整理后再测，记录触发方法和结束条件。
4. 将统计口径写入结果：不能直接以目录大小差代替累计写入量，也不能将引擎写放大当成 SSD 内部写放大。
