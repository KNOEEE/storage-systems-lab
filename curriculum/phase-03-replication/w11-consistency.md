# W11：写完之后，读取一定看到吗？

## 核心问题

复制日志的提交保证怎样转化为客户端读取保证？读取模式改变后，哪些结果仍然允许？

## 理论与设计（1.5 小时）

- DDIA 第一版第 9 章：线性一致性及其代价，区分它与事务隔离性。
- [etcd API 保证](https://etcd.io/docs/v3.6/learning/api_guarantees/)：Range 默认保证与 serializable 选项。这里的 API 名称不等于事务隔离级别“可串行化”。

## 目标源码（1 小时）

固定 etcd 提交，定位两种读取模式的分支，找出确认读取位置及等待状态机应用的位置。把 commit 和 apply 分开标在 W10 的图上。

## 验证步骤（2 小时）

1. 使用 W09 集群，写入递增编号，记录每次写响应与随后读请求的先后关系和 revision。
2. 针对指定节点分别执行默认读和 serializable 读，保留客户端参数与结果。
3. 在测试节点重启或追赶期间再观察一轮。若没有旧读，不代表两种模式具有相同保证；根据文档和实现列出允许出现但未观测到的情况。
4. 为线性一致读取写一个小历史示例，说明哪些响应顺序会违反保证。
