# W09：请求超时到底意味着什么？

## 核心问题

客户端没有收到成功响应，能否推断服务端没有执行写入？重试时应该怎样辨认同一业务操作？

## 理论与设计（1.5 小时）

- DDIA 第一版第 8 章：网络故障、超时与进程暂停；第 5 章单主复制入门。
- [etcd API 保证](https://etcd.io/docs/v3.6/learning/api_guarantees/)中与请求失败有关的说明。先列出“请求未到达”“已执行但响应丢失”等可能时序。

## 目标源码（1 小时）

固定 etcd 提交，定位客户端 Put、请求超时与错误返回路径；在服务端标出提案与最终响应的衔接。只追一次简单写入，不展开所有重试策略。

## 验证步骤（2 小时）

1. 按所装版本文档启动三个自己的测试节点，使用独立数据目录和端口，记录成员与健康状态。
2. 每个操作使用唯一编号并写入对应值，保留客户端起止时间、请求编号和返回结果。
3. 正常写入作为基线；再对少量请求设置短 deadline 或暂停一个测试节点，收集成功、明确拒绝和结果未知的样本。
4. 恢复后按操作编号查询最终状态，比较客户端结果。超时未出现或没有出现“超时但已写入”也是结果，不能编造故障样本。
